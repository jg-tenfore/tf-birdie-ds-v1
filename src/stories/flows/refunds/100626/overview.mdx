# Oct 6 — Create a Refund, as a modal

> **Option A was chosen** on Oct 7 by Weston, Austin and Jarrett. The work
> continued in **[100826](?path=/docs/flows-refunds-100826-overview--docs)**,
> which carries his notes and multi-refund. This folder stays as the record of
> the comparison — the two options as they were put side by side.

One screen is being redesigned: **Create a Refund**. Everything else in the
refund path stays as it is. Two options are drawn here so the shape can be
chosen on screens rather than in the abstract.

From the Oct 6 call with Weston:

> *"That doesn't make sense. So what these are doing is you're saying what you
> don't want to refund."*

> *"Keep it in the same design system. We don't need to do anything super crazy,
> but let's clean that up."*

So: same system, same reversal-order model, one screen replaced — and the
replacement is a **modal over the transaction**, because a refund is an act
performed on an order and the full-screen version loses that order the moment it
opens.

## The two options

| | **A — One pane** | **B — Stepped** |
| :-- | :-- | :-- |
| Shape | Items, tenders and reason on one surface, then a confirmation | Items → tenders + reason → done |
| Whole-order refund | Select all → reason → review → refund | Select all → Next → reason → refund |
| Tender split visible | While the basket is being chosen | One step later |
| Density | Scrolls at six lines plus two tenders | Nothing scrolls |
| Best when | The operator wants the whole picture before committing | The counter is busy and one question at a time is easier |

Both share every part — the item row, the split, the reason picker, the totals,
the completion screen. **There is one item row in this design, not one per
option**, so a decision between them is a decision about sequence and density,
not about components.

## Seeing the whole flow

Each option carries two comps of its full journey, after its individual states:

| Story | What it is |
| :-- | :-- |
| **End to end** | The flow, clickable: Order Lookup Results → the transaction → the modal → back to the list with the reversal order on it. Run A's, then B's, on the same refund |
| **Flow storyboard** | The same flow as comps on one sheet — every frame a real screen at 1280×800, scaled, with captions. Made to be screenshotted into a ticket or a deck |

The storyboards render the same components as the prototype, so a sheet cannot
drift away from what it documents. The walkthroughs write a **real reversal
order** from what was actually refunded: keep one Bubly Lime and the completion
screen, the list row and the record all say $46.46.

**Every row in the day's list opens**, and every sale on it can be refunded —
six lines on two tenders, a $414 driver on one card, two green fees on a single
line. The reversals in the list open as records with REFUND dead, because a
refund is not refundable; the device does offer it, which is recorded in the
as-is folder and left as a question for the ticket rather than quietly fixed
here. Eight of those orders are reconstructed to fit the row's id, time,
customer, tender and amount — the baskets are invented, the totals are not.

Against the as-is **6 — End to end** one level up, the comparison the sheets are
for: today's refund crosses seven surfaces and two full-screen loads; Option A
crosses five, Option B six.

## What changed, and why

| Fixed | How |
| :-- | :-- |
| Selection was inverted — full quantity pre-filled, you subtracted what the guest kept | Nothing is selected until it is chosen. **Select all items** makes the common case one tap |
| A kept line was a `0` in a stepper, identical to an included line | The checkbox carries inclusion; quantity is a second control inside a selected row, reading **1 of 2** |
| The tender split was invisible until after the refund | Each tender prints what it will take, live. Cash first — the rule the backend already applies, now stated |
| *"Price of selected payments is less than total price to be refunded"*, after a press | A sentence in dollars, inline, as it happens: *"$25.58 short. Add a tender, or refund fewer items."* |
| Tax had no line to go back on, so an $18.44 charge could only return $15.44 | Tax is prorated to the share being returned and shown as its own row. Refund everything and the whole charge comes back |
| A reason prompt that confirmed nothing, with no Cancel | Four reasons and a catch-all — short enough to answer honestly, fixed enough to report on — then a confirmation that restates the decisions and carries the amount on the button |
| The flow ended on a list, with a banner naming no order | It ends on the refund: amount, every destination, the reversal order number, and **Print receipt** — the ask from the call |

## How it is drawn

The paint is the app's, not a new one. Weston asked for a cleanup inside the
existing system, so these screens use what the product already has:

- the **navy dialog header** with a centred title, as every dialog in the app has;
- the **grey section band** that Transaction Details puts over *Order Items* and *Payments*;
- **4px corners**, square dark checkboxes, MD2 filled fields;
- **ALL-CAPS slate / green / red action buttons** — the same `ActionButton` the bottom bar uses, in the same three tones;
- the **warning orange** the device already shows a refund shortfall in.

These stories therefore render on the **replica theme**, like the as-is folder,
rather than the design system's target-state theme. One override: every control
sits on the **48dp touch floor** instead of the device's 40px, because this is
the screen that moves money.

## What deliberately did not change

- **A refund is still a reversal order.** Weston: *"it's a lot better that way,
  reporting-wise."* The design only names the new order instead of leaving it to
  be found.
- **Allocation is still cash first**, in the order tenders were taken. The rule
  is the backend's; this makes it legible.
- **Order Lookup, the results list and Transaction Details are untouched** in
  this folder. They are recorded as-is one level up.

## Open questions for the ticket

1. **Tax per line.** The design prorates it from the order total. If the backend
   can return tax per line, the summary should use that instead — it matters on
   mixed-rate baskets.
2. **Refunding to a tender that was not on the order** (cash back on a card
   sale). Not drawn: the current app does not allow it, and nobody has said
   whether it should.
3. **Permissions.** Nothing here asks who is refunding. If a manager PIN is
   wanted, the confirmation is where it belongs.
4. **The reason list.** Four plus `Other` is a starting set, not a decision. What `Other` collects in the first month should decide what gets promoted into the list.
5. **Already-refunded orders.** The modal does not yet show what a previous
   refund took off this order, which is the one place a double refund gets
   caught.
